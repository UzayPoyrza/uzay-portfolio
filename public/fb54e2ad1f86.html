A.Technical understanding

Open with this.

Q1
Say
My understanding is that this is a RAG system. Tickets and docs get chunked and embedded, and a question is matched against them by cosine similarity, usually as hybrid search with keyword scoring like BM25 alongside the vectors, with weights you tune, plus a reranker. The top results go into the model's context, and the agent uses tool calls to check live system state before suggesting a fix.
Ask
Is that roughly how yours works? What would be different in what you build for us?

Ask

D.Reliability and maintenance

Q9
Say
From my experience with RAG, retrieval scoring is fairly deterministic. So if a stale ticket or a bad match ranks highly, it will likely give the wrong answer every single time, and fixing it means changing the system, like removing that ticket or adjusting the knowledge base.
Ask
Who handles that after the POC, you or us? How does the system get better over time? I don't mean retraining the model, I mean tuning the system itself: the knowledge base, prompts, rules, and feedback from the admins using it.

Open angles

Debugging

Can we stream traces to our own store? What do we see if a Slurm tool crashes? Can admins see which chunks an answer used?

New angles, round 2

  1. Data sources beyond tickets: job analysis needs Slurm accounting plus GPU/CPU metrics over time. Which of our monitoring sources would they hook into, and do they build those connectors?
  2. Knowing who's asking: can the agent know the user's UNI, Slurm accounts and groups and tailor answers, like Michigan's ARCHIE? Through Columbia SSO?
  3. Cluster-specific answers: Insomnia, Ginsburg and Terremoto differ in partitions, storage and policy. How does the agent keep them straight?
  4. Grounding commands: when it suggests an sbatch line or module load, is that checked against our real partitions and modules, or generated from general knowledge?
  5. Keeping knowledge fresh: when docs change or new tickets close, is re-ingestion automatic? How often?
  6. Handoff package: when it escalates to a senior admin, what exactly is handed over (conversation, job IDs, logs, what it already tried)? Does it open or update the ServiceNow ticket?
  7. Silent changes: when IBM updates the platform or model, can behavior change without warning? Is there version pinning or regression testing?
  8. Side-by-side test: run their agent and a simple in-house baseline on the same set of past tickets during the POC, to show what IBM adds.
  9. Speed: how fast is an answer that needs several tool calls? It matters for an admin mid-incident.
  10. Demo video follow-up: on the prep call they promised to resend the demo video originally shared with Sam. Did it arrive?
